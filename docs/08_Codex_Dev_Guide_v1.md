## 1. 角色与工作方式

| 角色 | 职责 | 不做的事 |
|------|------|----------|
| 负责人 | 需求、裁决、内网操作、登录类交互（浏览器弹窗内登录） | — |
| 设计与评审主持 | 设计文档（00–09）、任务提示词、审读代码与证据、处置评审意见 | 不写、不运行项目代码，不以自己跑出的数值作证据 |
| 开发（Codex） | 按任务提示词实现、测试、产出证据、维护开发状态文件 | 不修改设计文档 00–09；不放宽门禁；不自行做设计裁决 |
| 外部评审（三家） | 评审设计与阶段 gate 的代码和证据，每条缺陷附候选修改方案 | — |
| 内网 AI | 在内网执行验证脚本并以文本回传结果 | 不做设计判断 |

工作规则：

1. **一次一个任务。** 每个任务由一份提示词下达，任务编号连续（task-001、task-002……）。重任务串行执行，不并行开两个会话改同一仓库。
2. **只实现已评审的契约。** 代码只实现已经三方评审通过的 01 条目（09 §2 原则 6）。尚未通过的条目若必须先写桩，按 §6.4 标为 provisional。
3. **发现设计问题时停下来报告。** 实现中发现 HLD / 01 / 09 有矛盾、缺口或无法实现之处：在任务报告的"设计问题"一节写明位置、现象和建议，不在代码里自行选一种解释继续。只有提示词明确授权的临时处理才可以继续，并登记为挂账。
4. **异常即停。** 以下情况立即停止并报告，不自行修复后继续：输入文件缺失或 sha256 不符；仓库状态与提示词描述不符（分支、HEAD、未跟踪文件）；门禁失败且修复需要放宽门禁、跳过或标记测试为预期失败；资源限制无法生效；需要凭据或需要访问提示词未列出的网络地址。
5. **不放宽门禁。** 不得降低覆盖率阈值、不得添加 `# type: ignore` / `# noqa` / `pytest.skip` / `xfail` 绕过失败，除非提示词明确授权并在开发状态文件登记理由与解除条件。

## 4. 开发机资源限制

开发机同时运行 VS Code 等交互程序，曾因任务占满 CPU 与内存而崩溃。以下规则对所有任务生效，提示词可以更严，不能更松。

### 4.1 分级

| 级别 | 适用 | 包装方式 |
|------|------|----------|
| L0 轻量 | git、文件移动、单个测试文件、小脚本 | `nice -n 19 ionice -c3` |
| L1 门禁 | 全量 pytest / coverage、mypy、ruff 全仓、import-linter、property / fuzz、故障注入套件 | `systemd-run --user --scope -p CPUQuota=200% -p MemoryMax=3G -p MemorySwapMax=0 nice -n 19 ionice -c3 <命令>` |
| L2 重负载 | gbs / mic 构建、构建 VM、大规模故障注入扫描 | 只在提示词明确授权时运行；默认 `-p CPUQuota=400% -p MemoryMax=8G -p MemorySwapMax=0`，提示词另定的以提示词为准 |

### 4.2 规则

1. L1 / L2 命令一律串行，不并行运行两组；pytest 不使用 xdist 等并行插件。
2. 运行前记录 `free -m` 与 `/proc/loadavg`；可用内存（`free -m` 的 available）低于该级 MemoryMax 加 1 GB（L1 即 4 GB）或 1 分钟负载高于 CPU 核数的一半时，等待至满足（最长 30 分钟），超时停止报告。（2026-11-11 负责人裁决：原"2 倍 MemoryMax"门槛过高，导致长时间等待，下调；MemoryMax 上限本身不变。）
3. `systemd-run --user` 不可用时停止报告，不得在无限制状态下运行 L1 / L2。
4. 运行时间可能超过 10 分钟的命令以 `setsid` 脱离终端运行，输出实时写入日志文件；结束时无论成败写一行带时间戳的结束标记（`ALL-END <时间> status=<ok|fail> rc=<退出码>`），能区分仍在运行、正常结束和中途退出。
5. 测试中的计时敏感用例在受限资源下失败时，单独重跑最多 3 次（同样受限）；3 次内通过记为"受限资源下偶发"并在报告列出，不放宽限制。
6. property / fuzz 测试分两档：门禁档（固定种子、有界样例数，保证 L1 下可完成）与深度档（只在提示词授权时运行）。

## 5. 门禁

### 5.1 门禁内容

`ci/gate.sh` 是门禁的唯一入口，本地以 L1 级运行；其结果是阶段 gate 证据的组成部分。门禁按顺序执行，任一项失败即整体失败：

1. **锁文件一致性**：锁文件与依赖声明一致，环境按锁文件安装。
2. **ruff**（lint + format 检查）。
3. **mypy --strict**（全部 `framework/`、`agents/`、`conformance/`、`ci/` 中的 Python 代码）。
4. **import-linter**（§3.2 的依赖边界）。
5. **pytest + coverage**：全局行覆盖 ≥ 80%；关键模块（`orchestration`、`ledger`、`approval`、`release`、`sdk` 的副作用部分）分支覆盖 ≥ 95%（HLD §11.2）。阈值写在配置中，修改阈值等同修改门禁，需评审。
6. **无 PHP 检查（D23）**：判定信号、分类、片段判据、签名表与扫描器 digest 按 HLD §11.2 实现。门禁覆盖仓库内容与已安装依赖闭包；主机安装集、镜像与部署前缀的扫描、E0 子进程观测与执行准入属于部署验收（HLD §11.2、09 §4.2），随对应阶段实现并纳入 gate 对照表。
7. **内容边界扫描**（§2.4）。
8. **契约一致性**（自 contracts 包落地起）：`contract_version` 与 01 文档版本头一致；01 A0 列出的模型均可导入且字段与文档一致（由提示词给出比对方法）。
9. **CF 追溯检查**（自 contracts 包落地起）：每个已实现的 01 CF 用例编号都有对应测试（§6.2），未实现的列入报告，不得静默缺失。

### 5.2 门禁输出

门禁运行生成 `gate_report.txt`：仓库 HEAD、时间、解释器与锁文件 digest、每项结果与耗时、覆盖率摘要、资源包装参数、`ALL-END` 标记。阶段 gate 证据引用该文件及其所在提交。

## 6. 编码与测试规范

### 6.1 编码

- 全部代码带类型标注，满足 mypy --strict；公共函数与类写英文 docstring；代码注释用英文，文档用中文。
- 契约模型用 pydantic v2，字段名、类型、取值、默认值与 01 逐字一致；需要不可变的模型设为 frozen。
- 不使用模块级可变全局状态；时间、随机数、UUID、子进程、文件系统与网络访问经可注入的接口获取，测试中替换为确定性实现。
- 子进程只经框架的受管调用接口启动，不使用 `shell=True`；不在代码中拼接 shell 命令字符串。
- 错误以 01 定义的错误码 / 原因码表达，不以自由文本作为判定依据。
- 持久化写入只经 Ledger 接口；每个 Ledger 提交点有稳定名称，供故障注入枚举（HLD §11.3）。
- 日志结构化输出，不写入凭据与发往 LLM 的原始数据；需要记录的敏感数据按数据边界规则处理。

### 6.2 测试

- 目录：`tests/` 下按被测包分目录；Agent 包测试放在各自包内。
- pytest 标记：`unit`、`contract`（01 CF 用例）、`property`、`faultinj`（逐持久化边界故障注入）、`model`（状态机 model-based）、`e2e_fake`（全 Fake 依赖的端到端）、`intranet`（只在内网运行，开发机自动跳过并在报告中计数）。
- **CF 追溯**：01 的每个 CF 用例对应至少一个测试，用 `@pytest.mark.cf("CF-AUTH-20j")` 标注；门禁据此生成追溯报告（用例编号 → 测试 → 结果），CF 用例中的每一格（如 R22、R23 格）各自有断言。
- 测试不访问网络（以夹具强制）；外部依赖一律用 Fake：FakeLLM、FakeBoardPool、FakeQuickbuild、FakePublisher（HLD §10）。Fake 的行为本身有测试，Fake 与真实实现共用同一接口的合规测试。
- 负向夹具中需要出现 PHP 标记、伪凭据等内容时，在测试运行时拼接生成，不以字面量落盘（与 HLD §11.3 一致）。
- §11.3 的强制测试类别按阶段落地，P1–P4 gate 前逐类完成（见 gate 对照表）。

### 6.3 Fake 与真实实现

- 外网开发机上只运行 Fake；真实实现的单元测试可以在开发机运行，联调标记为 `intranet`。
- 内网联调按 09 §2 原则 3 集中安排：开发产出验证脚本与预期结果，由内网 AI 执行，结果以文本回传，经负责人转交；内网产物不进仓库，只登记经负责人确认可外传的摘要（§2.4）。

### 6.4 provisional

- 尚未三方通过的契约条目若必须先写，代码中以 `PROVISIONAL(<映射表子键>)` 标注（注释或常量），并登记在 `docs/dev/provisional.md`：位置、对应映射表子键、预计通过日期。
- 门禁统计 provisional 数量并写入 `gate_report.txt`；阶段 gate 验收时，该阶段生产或消费的条目不得仍为 provisional（HLD §13、09 §3.1）。

## 7. 开发记录与交付

### 7.1 开发状态文件 `docs/dev/STATUS.md`

每个任务收尾时在同一提交中更新；新的开发会话开场先读它，与仓库实际状态核对，不一致先报告。内容：

3. 已闭合结论：结论、证据路径、提交号；
4. 负责人裁决前提（逐条，注明日期与来源）；
5. 挂账：问题、临时处理、解除条件、负责方；
6. 环境事实：解释器版本、锁定工具、`systemd-run --user` 可用性等（附核实命令与日期）；
7. 设计问题清单（§1 规则 3 报告过的，注明处置状态）。

### 7.2 跟踪表

- `docs/dev/gate_matrix.md`：HLD §13 每项交付件与 gate → 负责人、日期、证据路径（09 §10）。M0a 前完成 P0–P2 部分，1-22 前完成 P3–P4 部分，01 第三批通过前完成 P5–P7 部分。
- `docs/dev/01_extension_mapping.md`：HLD 附录 B 第 7 组逐条映射（09 §3.1）。以附录原文逐条编号为键，跨批时拆"编号 + 字段组"子键；列出 schema / 命令 / 迁移 / CF 用例、最早使用方、所属批次、三方通过日期、实现日期、阶段验收日期，以及 P1–P4 gate 所跑 §11.3 各类别消费的条目。批次分配由设计审定，开发负责抽取条目与维护日期。
- `docs/dev/provisional.md`（§6.4）。

### 7.3 任务交付目录

每个任务的交付放在 `docs/dev/deliver/task-NNN/`，目录中只放交付文件，全部为纯文本（`.md` / `.txt`），不放压缩包：

- `REPORT.md`：完成了什么、没完成什么及原因、设计问题、挂账变化、新增依赖；
- `gate_report.txt`：本任务最后一次门禁输出；
- `evidence.txt`：关键命令与原始输出（超过 2 MB 拆分为 `evidence_1.txt`……）；
- 提示词要求的其他文件。

任务回复只写简短摘要：提交号、交付目录、门禁结果、需要负责人或设计处理的事项。

### 7.4 结论的证据等级

报告中的每个验收结论标明证据等级：**真实**（真实依赖、真实环境）、**Fake**（Fake 依赖）、**人工**（人工操作得出）、**未验证**。Demo 与阶段 gate 不得以 Fake 等级的结论替代要求真实验证的项（09 §4.3）。

## 8. 阶段 gate 的证据要求

每个阶段 gate 提交外部评审的证据包包括：

1. gate 对照表中该阶段全部行的证据路径，无空项；
2. 对应提交上的 `gate_report.txt`（门禁全部通过）；
3. CF 追溯报告：该阶段生产或消费的 01 条目全部有测试且通过，无 provisional；
4. HLD §11.3 中该阶段要求的测试类别报告（含故障注入的提交点清单与逐点结果）；
5. 安全切片验收记录（适用时）：构建隔离、ClineSR CLI OS 层约束与数据边界、D23 部署验收（09 §4.2），注明证据等级与执行环境；
6. 内网联调记录（适用时）：脚本、执行环境、结果摘要与负责人确认；
7. 已知问题与挂账清单。

各阶段的具体 gate 以 HLD §13 为准；Demo（M1）的验收以 09 §4.3 为准。评审意见按严重程度处置，阻断项修复后才能进入下一阶段（09 §10）。

## 9. 待负责人确认与待评审的选择

| 项 | 本稿的选择 | 理由 |
|----|-----------|------|
| 分支策略 | 在 `main` 上开发，不开任务分支 | 单开发会话串行，任务分支只增加合并成本；评审在已推送提交上进行，问题以后续提交修正 |
| 锁定工具 | 建议 uv，开发确认可用后定 | 速度快，锁文件含哈希；不可用时改用 pip-tools 并记录 |
| 托管 CI | 暂不启用，以本地 `ci/gate.sh` 为准 | 门禁结果须绑定资源限制与提交号；是否另开 GitHub Actions 镜像由负责人决定 |
| 门禁资源档 | L1 为 2 核、3 GB | 与此前各线的限制一致；若全量测试在此限制下超过 30 分钟，再评估调整 |
