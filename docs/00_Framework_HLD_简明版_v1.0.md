## 一、这是什么

一条**自动化软件工程流水线**：外部的 Coding Agent（ClineSR，过渡期用 Codex）针对 Tizen 代码生成修改 patch，交给我们的框架后，框架内的五类 Agent 依次完成——编译并自动修复编译问题（Compiler）、上板跑单测（UT）、跑性能基准（Benchmark）、AI 审查汇总报告（Review）、人工批准后发布到 gerrit/github（CI + 发布组件）。全程可追溯、可断点恢复、出错有兜底，发布必须过人工这一关。

我们团队交付的是**框架本身 + 公共模块 + 发布安全组件 + 一个作为样板的 Compiler Agent**；UT / Benchmark / Review / CI 四类业务 Agent 由各业务团队按我们提供的设计指引和合规测试套件二次开发。（完整版 §1）

## 二、一个 patch 的旅程（旗舰流水线）

1. **锁定基线**：Coding Agent 调用框架接口创建一次 Run，框架当场拉取最新 Tizen 代码并"拍照"（snapshot）——之后整条流水线都基于这张照片工作，中途绝不追新代码，保证 patch 永远打得上。
2. **提交 patch**：Coding Agent 基于该 snapshot 生成 patch series 提交。框架校验能否干净应用，不能就当场拒绝。
3. **编译与自动修复**：Compiler Agent 打上 patch 编译，失败则分析报错、自己产修复 patch 再编译——修复次数有硬上限，超限不硬撑，直接打包全部证据走失败兜底。编译通过后还会按依赖图把受影响的关联包一起编出来。
4. **并行推进**：编译通过后，UT 验证（装板、跑测试、失败可有限轮次回流修复）与静态代码审查并行走。UT 通过后跑 Benchmark，性能回归超过阈值会被一个纯代码判定的关卡拦下。
5. **汇总审查**：Review Agent 拿到 UT 结果、Benchmark 结果、静态审查结果，出一份带完整出处的最终审查报告——patch series 的每一段都标着"谁、哪一轮、为什么改的"。
6. **人工关卡**：CI Agent 先生成一份"发布计划"（发到哪、发什么、基于哪个版本），**人工 reviewer 在命令行工具里看到并批准的就是这份计划本身**。批准动作在账本里生成一条一次性授权。
7. **发布**：发布由一个独立的、唯一持有发布凭据的框架进程（release broker）执行——它核销那条授权（一次性、绑定发布内容的摘要，内容有任何变化授权自动作废），然后推送 gerrit/github。业务 Agent 从头到尾摸不到发布凭据。
8. **失败与打回**：任何环节超限或人工 reject，流水线进入统一的失败兜底：聚合所有轮次的 patch、报错、测试结果、审查意见，生成一份完整的反馈报告，交回 Coding Agent 的开发人员分析。修复后作为新 Run 重新进入，新旧 Run 之间有链条可追溯。（完整版 §2.2 表、§4.2.1 示例、§8）

## 三、几个最重要的设计决策（说人话版）

**1. 流水线是配置出来的，不是写死的。** 整条流水线是一份 YAML 文件：哪些节点、结果怎么路由、循环最多几轮、哪里要人工批准。想只跑"编译 + Benchmark"做测试？换一份配置文件，一行代码不用改。配置在加载时会被一套静态校验器检查——路由有没有漏、循环有没有上限、发布前有没有人工关卡、并行汇合点会不会永远等不齐——不合法的流水线根本起不来，而不是跑到一半死给你看。这套静态检查是十一轮评审里打磨最狠的部分。（§4.2）

**2. 发布安全是物理隔离，不是流程约定。** 三道闸：配置校验器拒绝任何"不经人工批准就能到发布节点"的流水线；发布凭据只存在于 broker 独立进程，业务 Agent 的运行环境里根本没有这个通道；授权一次一条、绑定具体内容摘要、原子核销。哪怕某个 Agent 的代码被写坏甚至被骗（patch 是 LLM 生成的，提示注入是真实风险），它也发不出任何东西。（§8）

**3. 崩溃恢复按"最坏情况"设计。** 框架承诺的是"至少执行一次"而不是"恰好一次"——所以每个昂贵操作（编译、刷板、发布）都有幂等保护：执行前先在账本记意向，恢复时先问外部世界"这事到底做没做"（能查的查、声明可安全重做的重做、都不行的如实报错停下），绝不瞎猜。编译一次几十分钟，"恢复后又重编了一遍"或者"以为编过了其实没编"都是真金白银的事故。（§5.2）

**4. 全系统只有一本账。** 一个 SQLite 账本是唯一权威事实源：Run 状态、每次执行、每个产物、每条授权、每次核销，同一事务提交。审计、恢复、追责都只看这本账；编排引擎（内部用 LangGraph，但被硬封装在一个模块里，理论上可整体替换）的内部状态只是执行加速器，不是事实来源。（D1/D6）

**5. 人不用一直盯着，但关键处必须是人。** 人工批准可以挂几天（挂起时段不消耗任何预算），批准前 patch 内容有任何变化，旧授权自动作废、必须重审。发布后极端情况下状态不明（比如推送瞬间断网），有一套人工裁决协议：必须附远端证据才能裁决，裁决后系统还会继续盯 24 小时防"迟到的推送"，发现了就告警留痕、绝不静默。（§4.4、§8.3）

**6. 内网数据出不去。** 每份数据在产生时就带密级标签（源码、构建日志各有等级），聚合时取最高级，任何 LLM 调用前框架强制校验目标模型是否被授权接收该密级——不靠调用方自觉。开发期外部模型只喂 fixture 假数据。（D7、§7.1）

## 四、给业务团队的话：你们拿到什么

- **SDK**：继承一个基类、实现一个 execute 方法、声明你的结果枚举，其余（幂等、追溯、超时、上下文组装、知识查询）框架代管。你的代码跑在独立子进程里，框架管生杀。
- **公共能力**：CodeGraph（代码调用链/符号查询）和 LLM Wiki（知识库）以统一接口注入，可换成你们自己的知识源；给 LLM 喂证据有现成的证据包工具链（防止把原始日志直接灌给模型这类低级错误，是我们踩过坑固化下来的）。
- **每类 Agent 一份设计指引**（02–06 文档，后续产出）：职责边界、输入输出契约、必须遵守与建议参考严格分开。
- **合规测试套件 + 可运行空壳 + 本地 harness**：你的 Agent 过了合规测试才能接入流水线；没有完整环境（没板子、没内网 LLM）也能在本地用 mock 编排器开发调试。（§5、§7、后续 07 文档）

## 五、出了问题会怎样

任何环节的失败都有明确归宿：修复循环超限 → 兜底；系统级异常（进程崩溃、超时）→ 默认兜底（可配置有限重试）；性能回归超阈值 → 拦截；人工 reject → 兜底。兜底不是"报个错完事"，而是把整个 Run 的所有证据（每轮 patch 及出处、报错、分析、测试与基准结果、AI 审查意见）打包成一份反馈报告。版本漂移（框架/Agent 升级后遇到旧的执行现场）不做危险的"带病恢复"，直接对账收尾。每个 Run 关闭时都有一份终局摘要，事后如果发现与远端事实不符（前述迟到发布），以只增不改的修正记录附联——历史永远不被改写，但真相永远可见。（§4.3、§8.3）

## 六、技术底座一览

Python 3.12+；编排引擎 LangGraph（锁定版本、硬封装、可替换）；SQLite 账本；单机部署；monorepo；质量门禁 pytest 覆盖率 ≥80%（关键模块分支 ≥95%）+ mypy strict + ruff + 架构规则强制（import-linter）。明确不做的：分布式多机、多租户、学习型模型路由、通用工作流引擎、完整容器沙箱（信任模型与残余风险已显式登记）。（§1.3、§11）
