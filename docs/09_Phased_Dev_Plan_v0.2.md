## 2. 计划原则

1. **先打通一条真实的竖切片，再横向补齐。** 12 月 Demo 不追求覆盖全部阶段，而是让"提交 patch → 真实构建 → AI 定位并修复失败 → 人工审批 → 模拟发布"真实跑通。Demo 用到的部件都按正式设计实现，不写一次性演示代码。Demo 只实现契约的一个明确子集（§4.2），子集以外的路径一律失败即停。Demo 之后在其上补齐各阶段 gate。
2. **AI 的作用必须看得见、可对比。** 总部关注"是否为了用 AI 而做 Agent"。每个 Agent 的演示与验收都同时给出两条路径，差异用测试结果说明，不靠描述：
   - "无 AI 路径"：框架照样跑完构建、测试、报告、审批；
   - "有 AI 路径"：定位原因、给出修复或优化，并以测试结果验证。
3. **能在外网开发机完成的先做，内网联调集中安排。**
   - 外网开发机以 Fake 实现替代内网依赖（LLM、板子、Quickbuild、发布端点）。
   - 内网 LLM（ClineSR CLI）、Quickbuild、Cosmos、内网板子与真实发布端点只能在内网验证。这部分按批集中安排，由内网 AI 执行验证脚本，结果以文本回传。
4. **按阶段 gate 验收。** 每个阶段的完成以 HLD §13 的 gate 为准。代码与证据经外部评审后才算通过，不以"写完了"计。HLD 每一项交付件与 gate 都对应到负责人、日期和证据路径（§10），有缺项不得以"全部 gate 通过"结案。
5. **安全底线不为进度让步。** Demo 阶段同样遵守，且不在任何降级范围内：
   - 构建隔离（不在宿主以 root 直跑；独立构建主机须满足相同的不可变基底与每次复位契约）；
   - 发布凭据只在 broker；
   - 人工审批；
   - 超时不得当通过；
   - 不得引入 PHP；
   - **ClineSR CLI 的 OS 层约束**（专用 OS 用户、出口仅内网 LLM 端点、由 launcher 拉起、工具关闭、close_fds、只读输入）；
   - **发往 LLM 的数据边界 fail-closed**。
   Demo 用到的切片，其安全门禁在首次真实使用前完成验收，不推迟到对应阶段的完整 gate。
6. **契约先行。** 代码只实现已经三方评审通过的契约部分。尚未定稿的字段在代码中显式标为 provisional；对应批次未定稿，相关阶段的 gate 不能宣称完成（§3.1）。
7. **人力基线（负责人 2026-11-11 确认）。** 本计划按以下产能排期。产能变化或月度偏差超过一周时，按 §10 重排：
   - 负责人：需求、决策与内网操作；
   - 设计与评审主持：1 人；
   - 开发：Codex 开发会话，重任务串行、严格限制 CPU 与内存；
   - 外部评审：三家；
   - 内网验证：由内网 AI 执行。

## 4. M1：2026 年 12 月 Demo

### 4.1 Demo 演示内容

**场景**：开发者在 Coding Agent（先用 Codex）中经 Skill 提交一个 Tizen 公开代码的 patch，并指定目标模块。框架自动完成以下流程：

1. **启动与范围**：经 MCP 服务启动 Run，记录目标模块与基线。演示同一框架下两种流水线子集（仅构建；构建 + 后续 Agent），说明 Agent 可增删。
2. **真实构建**：本地 gbs 在构建隔离边界内，构建 patch 及受影响的包；时间允许时再用 mic 出镜像。
3. **Compiler Agent 的 AI 修复（核心）**：选取 Clang 迁移中真实出现过的构建失败，2–3 个，类型各不相同。
   - **无 AI 路径**：框架报告失败，给出日志定位与失败包清单，流程停在明确的失败结论上。
   - **有 AI 路径**：LogAnalyzer（含编译错误经验库）结合内网 LLM 分析根因，生成修复 patch，框架重新构建验证。修复是否成立以重新构建的结果为准，不以 AI 自述为准。
4. **后续 Agent**：UT、Benchmark、Review、CI 先以符合契约的空壳 Agent 接入（输出固定的合规报告），只用来证明流水线结构与即插即用，不演示它们的真实能力。
5. **人工审批**：在审批 CLI 中查看完整证据，包括每轮构建结果、AI 修复前后对比、超时与重试清单（重试成功的条目须审批人逐条确认）。
   - 审批通过后，由 Release broker 发布到**模拟 gerrit**；
   - 审批拒绝时，向开发者生成汇总反馈报告。
6. **可靠性**：演示中途强制结束编排进程后重启，Run 从持久化状态继续：已执行的构建不重复执行，已核销的授权不重复发布。

**Demo 不包含**：真实板子测试、真实性能测试、优化、Quickbuild、VD、向真实 gerrit / github 发布。
- 前五项在 M2 前按 M2 的范围逐项验收（优化在 M2 只含 AutoFDO）；
- VD 在 M3 阶段完成。

### 4.2 Demo 实现的契约子集

**完整实现**：
- 01 的数据模型与 Ledger 落账；
- Run 状态机的正常路径与编排进程重启恢复；
- 审批授权与单次核销；
- Release broker 的正常发布路径、实例 epoch 与连接守卫、DispatchReceipt 出向协议。

**Demo 期间失败即停（fail-closed）**：01 §2.2d 中的以下部分在 M1.5 前完成，Demo 期间不实现：
- broker 崩溃后的自动恢复、恢复臂对账、只探测；
- K1–K6 的计数、暂停与重派。

失败即停的具体要求：
- broker 失联时 Run 保持 publishing 并告警；
- 不自动重派、不自动结案，由人工处理；
- Demo 只演示编排进程重启。

**Demo 用到的安全切片在首次使用前验收**：
- 首次真实构建前：构建隔离（不可变基底、每次复位、无凭据导出通道）。
- 首次真实 LLM 调用前：ClineSR CLI 的 OS 层约束与数据边界 fail-closed。验收内容为：
  - 专用用户运行、工具关闭、出口仅内网 LLM 端点；
  - 注入一条诱导执行命令的日志，确认没有文件写入或进程派生；
  - 未标注密级来源的载荷拒绝发送。

### 4.3 Demo 的验收标准

**原版验收**：
- 从提交到审批的全流程在 Demo 环境中连续跑通至少 3 次，除审批外无人工干预；
- 至少 2 个真实构建失败由 Compiler Agent 自动修复，并经重新构建验证；每个失败都给出有 AI 与无 AI 两条路径的结果对比；
- 结果中的超时、重试、未完成项全部显式呈现；
- 编排进程中途重启后，Run 正确续跑；
- kill broker 时，Run 保持 publishing 并告警，无自动重派；
- §4.2 的安全切片已验收；
- 用到的代码已通过对应部件的单元测试与契约合规测试，并经评审。

**降级版验收**：若按 §4.6 降级，另列一张降级版验收表，逐项写明哪些项未满足以及补验日期。不得以"可以展示"标记原版验收全部通过。

## 5. M2：2027 年 6 月底主要功能

### 5.1 M2 的范围与验收标准

M2 = **Tizen 全流水线可供真实开发者使用**。验收要求如下：

- **框架**：P1–P4 全部 gate 通过（M1.5）；契约 v1.0 定稿，含核心面与 Compiler / UT / Review / CI 面，这四类消费者均已合规接入；Benchmark / Optimization / Profile 相关面标注为 provisional。
- **Compiler Agent**：
  - 本地构建（RPM + 镜像）与 Quickbuild 两种后端都可用；
  - Quickbuild 能力按 HLD §7.6.1 的证据等级逐项验收，未通过验收的用途由校验器拒绝，不启用；
  - 在真实失败样本集上给出修复成功率与误修率。
- **UT Agent**：板子池接入第一个真实板型（RPi4），刷机、上电检测、测试执行全自动；接入业务部门提供的第一批 UT 测试用例。
- **Benchmark Agent**：通过 TPMS 适配器在真实板子上做 A/B 测量，可复现；BenchPolicy 统计判定通过 golden 用例。
- **Optimization Agent**：AutoFDO 方法插件，复用 AutoFDO/BOLT 线的增强版 llvm-profgen。在至少一个目标模块上有实测收益；无收益或 UT 失败时确定性撤销。
- **Review Agent**：AI 审查与人工审查两段，外接知识库接入业务部门的首批内容。
- **CI Agent**：官方 gerrit / github 发布 adapter。真实端点联调由负责人在受控环境完成后，才对生产目标开放。
- **运维出口**：publishing 滞留、manual_only、部分发布等情形可经运维 CLI 按 01 §5.1 收尾，裁决受已记录观测约束。真实端点联调前，在受控测试仓上演练一次 publishing 滞留的人工处置。
- **多版本对比报告**：至少包含基线、开发者改动、AI 优化后三列，以及构建、UT、Benchmark 三类结果；逐轮历史照常保留。
- **试用**：至少 2 个目标模块（建议从 kernel-rpi、Multimedia、Chromium 中选）由真实开发者试用一轮，并收集反馈。

### 5.3 M1.5 与 M2 的检查点

- **2-12（M1.5 进度检查）**：P4 落后一周以上时，M1.5 后延至 3-12。3 月工作相应顺延一周，以 7 月余量吸收。

- **llvm-profgen 延误或无收益**：在 M2 报告中写明 AutoFDO 收益一项未达，由负责人显式调整里程碑。不以"无 AI 也可用"替代收益验收。

## 10. 跟踪方式

- **周跟踪**：每周五对照本计划更新进度。偏差超过一周的项目写明原因和补救措施，同时核对人力基线是否仍成立。
- **月度更新**：每月底更新本文档，调整下月计划；同步 §1 的状态与 §7 的日期。
- **gate 对照表**：维护"HLD §13 每项交付件与 gate → 负责人、日期、证据路径"的一一对应表，阶段验收时逐项反查。例如：
  - P2 含 Build Gateway 骨架与 HTTP 端点；
  - P4 含逐轮对比报告与验证资产触及检查；
  - R13 的运维 CLI 与 R14 的 post-close correction 入 M1.5。
  缺项则验收不通过。
- **阶段 gate**：每个阶段的代码与证据经外部评审后才算完成。评审意见按严重程度处置，阻断项修复后才能进入下一阶段。
- **开发状态记录**：在仓库的固定路径维护开发状态文件，内容包括计划、进度、已闭合结论及其证据路径、负责人裁决前提、挂账项。每个任务收尾时在同一个 commit 中更新；新的开发会话开场先读它核对。
