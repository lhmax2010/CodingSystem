## 2. 计划原则

1. **先打通一条真实的竖切片，再横向补齐。** 12 月 Demo 不追求覆盖全部阶段，而是让"提交 patch → 真实构建 → AI 定位并修复失败 → 人工审批 → 模拟发布"真实跑通。Demo 用到的每个部件都按正式设计实现，不写一次性演示代码；Demo 之后在其上补齐各阶段 gate。
2. **AI 的作用必须看得见、可对比。** 总部关注"是否为了用 AI 而做 Agent"。每个 Agent 的演示与验收都同时给出"无 AI 路径"（框架照样跑完：构建、测试、报告、审批）和"有 AI 路径"（定位原因、给出修复或优化、并以测试结果验证），差异要用测试结果说明，不靠描述。
3. **能在外网开发机完成的先做，内网联调集中安排。** 外网开发机以 Fake 实现替代内网依赖（LLM、板子、Quickbuild、发布端点）；内网 LLM（ClineSR CLI）、Quickbuild、Cosmos、内网板子与真实发布端点只能在内网验证，按批集中安排，由内网 AI 执行验证脚本，结果以文本回传。
4. **按阶段 gate 验收。** 每个阶段的完成以 HLD §13 的 gate 为准；代码与证据经外部评审后才算通过，不以"写完了"计。
5. **安全底线不为进度让步。** 构建隔离（不在宿主以 root 直跑）、发布凭据只在 broker、人工审批、超时不得当通过、不得引入 PHP——Demo 阶段同样遵守。

## 4. M1：2026 年 12 月 Demo

### 4.1 Demo 演示内容

场景：开发者在 Coding Agent（先用 Codex）中经 Skill 提交一个 Tizen 公开代码的 patch，指定目标模块，框架自动完成以下流程：

1. **启动与范围**：经 MCP 服务启动 Run，记录目标模块与基线；演示同一框架下两种流水线子集（仅构建、构建 + 后续 Agent），说明 Agent 可增删。
2. **真实构建**：本地 gbs 在构建隔离边界内构建 patch 及受影响的包；时间允许时再用 mic 出镜像。
3. **Compiler Agent 的 AI 修复（核心）**：选取 Clang 迁移中真实出现过的构建失败（2–3 个，类型不同）。
   - **无 AI 路径**：框架报告失败、给出日志定位与失败包清单，流程停在明确的失败结论上。
   - **有 AI 路径**：LogAnalyzer（含编译错误经验库）结合内网 LLM 分析根因，生成修复 patch，框架重新构建验证；修复是否成立以重新构建的结果为准，不以 AI 自述为准。
4. **后续 Agent**：UT、Benchmark、Review、CI 先以符合契约的空壳 Agent 接入（输出固定的合规报告），以证明流水线结构与即插即用；不演示它们的真实能力。
5. **人工审批**：在审批 CLI 中查看完整证据。证据包括每轮构建结果、AI 修复前后对比、超时与重试清单（重试成功的条目须审批人逐条确认）。审批通过后由 Release broker 发布到**模拟 gerrit**；审批拒绝时向开发者生成汇总反馈报告。
6. **可靠性**：演示中途强制结束编排进程后重启，Run 从持久化状态继续，已执行的构建不重复执行、已核销的授权不重复发布。

**Demo 不包含**：真实板子测试、真实性能测试、优化、Quickbuild、VD、向真实 gerrit / github 发布。这些在 M2 前逐项完成。

### 4.2 Demo 的验收标准

- 从提交到审批的全流程在 Demo 环境中连续跑通至少 3 次，无人工干预（审批除外）；
- 至少 2 个真实构建失败由 Compiler Agent 自动修复，并经重新构建验证；每个失败都给出有 AI 与无 AI 两条路径的结果对比；
- 结果中的超时、重试、未完成项全部显式呈现；
- 编排进程中途重启后，Run 正确续跑；
- 用到的代码已通过对应部件的单元测试与契约合规测试，并经评审。

## 5. M2：2027 年 6 月底主要功能

### 5.1 M2 的范围与验收标准

M2 = **Tizen 全流水线可供真实开发者使用**。验收要求如下：

- **框架**：P1–P4 全部 gate 通过（2 月底完成，见 M1.5）；契约 v1.0 定稿（核心面与 Compiler / UT / Review / CI 面；Benchmark / Optimization / Profile 相关面标注为暂定）。
- **Compiler Agent**：本地构建（RPM + 镜像）与 Quickbuild 两种后端都可用。Quickbuild 能力按 HLD §7.6.1 的证据等级逐项验收，未通过验收的能力不启用。在真实失败样本集上给出修复成功率与误修率。
- **UT Agent**：板子池接入第一个真实板型（RPi4），刷机、上电检测、测试执行全自动。接入业务部门提供的第一批 UT 测试用例。
- **Benchmark Agent**：通过 TPMS 适配器在真实板子上做 A/B 测量，可复现；BenchPolicy 统计判定通过 golden 用例。
- **Optimization Agent**：AutoFDO 方法插件，复用 AutoFDO/BOLT 线的增强版 llvm-profgen。在至少一个目标模块上有实测收益；无收益或 UT 失败时确定性撤销。
- **Review Agent**：AI 审查与人工审查两段，外接知识库接入业务部门的首批内容。
- **CI Agent**：官方 gerrit / github 发布 adapter。真实端点联调由负责人在受控环境完成后才对生产目标开放。
- **多版本对比报告**：基线、开发者改动、AI 优化后三列，含构建、UT、Benchmark。
- **试用**：至少 2 个目标模块（建议从 kernel-rpi、Multimedia、Chromium 中选）由真实开发者试用一轮，并收集反馈。

## 10. 跟踪方式

- **周跟踪**：每周五对照本计划更新进度；偏差超过一周的项目写明原因和补救措施。
- **月度更新**：每月底更新本文档，调整下月计划。
- **阶段 gate**：每个阶段的代码与证据经外部评审后才算完成；评审意见按严重程度处置，阻断项修复后才能进入下一阶段。
- **开发状态记录**：在仓库的固定路径维护开发状态文件，内容包括计划、进度、已闭合结论及其证据路径、负责人裁决前提、挂账项。每个任务收尾时在同一个 commit 中更新，新的开发会话开场先读它核对。
