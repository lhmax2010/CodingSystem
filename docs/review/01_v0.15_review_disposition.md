# 01_Contract_Spec v0.15 第十五轮三方复审处置表（→ v0.16）

裁决输入：Kimi **GO**（0 / 0 / 0 / 0）；Claude Code **NO-GO**（0 BLOCKER / 1 MAJOR / 0 MINOR / 1 NIT）；Codex **NO-GO**（0 BLOCKER / 2 MAJOR / 0 MINOR / 1 NIT）。合计 5 条意见，**全部采纳**。三个 MAJOR 是三个不同的问题，均出在上一轮新增的"失联次数上界"周边。

三家一致确认：新旧实例并存期间没有双重执行；上一轮两处取舍（未核销任务达上界后按发布失败关闭、新实例不等旧实例回收即上线）理由成立，Claude Code 撤回了本方原方案。

contract_version 由 1.0.0.dev4 升至 **1.0.0.dev5**。

## MAJOR

| # | 问题 | 来源 | 处置与采用方案 | 理由 |
|---|------|------|---------------|------|
| V1 | 已核销任务失联次数耗尽后"只经人工裁决收尾"，但人工裁决的守卫要求"强制 probe 后结果为 unknown"——远端其实已确定发生或未发生时，反而没有出口 | Codex C15-01 | **采用 Codex**：耗尽时置 `recovery_mode = manual_only`；人工裁决守卫增加 manual_only 分支，裁决前仍做只读强制 probe，且裁决受 probe 结果约束（全部发生只能确认已发布，全部未发生须原持有者静默后才能确认未发布） | 保留"耗尽后只人工收尾"的取舍，只是把人工出口打开，且不允许与远端事实相反的裁决 |
| V2 | 等待旧持有者静默期间阶段计时没有失效：同实例上本来正常的任务 B 的旧期限会到期，被另算一次失联；触发者 A 的同一到期事件也可能被重复计数 | Codex C15-02 | **采用 Codex**：期限绑定（阶段代次、所属实例 epoch），到期事务 CAS 消费一次，同事务解除该实例上全部任务的定时器；等待旧持有者期间不运行执行期限；新派发才重新武装；launcher 的退役 / 替换请求幂等 | W3 让"新实例已上线、旧实例迟迟未回收"成为正常状态，这个窗口必须有明确的计时规则 |
| V3 | 失联上界只计阶段期限到期；"毒丸任务"每次执行都让 broker 崩溃，走的是租约失效路径、不计次，仍会无限重派，每轮还中断同实例上的其他发布 | CC C15-01 | **采用 CC**：新增 `interrupt_count`——实例被回收时，该实例上处于执行可能阶段（等待结果或等待对账）、且不是本次失联触发者的每个任务 +1；上限缺省 3（高于失联上限 2，给无辜的连带任务留余量），达到后同样置 manual_only。launcher 拉起改为指数退避，连续多次启动即崩溃则停止自动拉起并告警 | 与 V2 合并后，触发者计 loss、连带者计 interrupt，两种计数互不重复 |

## NIT

| # | 问题 | 来源 | 处置 |
|---|------|------|------|
| V4 | CF-AUTH-20 与 CF-IPC-10 的预期仍写"回收完成后才恢复""已核销须先静默"，与上一轮的新实例不等回收、probe 发送不需静默不一致 | Codex C15-03 | 采用，预期按 execute（未核销 / 已核销）与 probe 分别写明 |

## 下一轮建议

三个 MAJOR 都在同一组机制（失联、中断与人工收尾）上，已一并补齐，未新增命令。建议**再做一轮定向核对**，只看 v0.16 的改动与 HLD v2.6 的 purpose 规则；若届时无 MAJOR，即可结束这一阶段的评审。
