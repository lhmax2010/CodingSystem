## "毒丸识别转实现期"问题的回答（不计入缺陷）

**结论：可行，而且建议采纳。** 契约层保留安全底线和"每个自动重试循环都有界、耗尽时都落在安全出口"两类规则。"谁是毒丸"的归因精度改为实现期策略，以运行数据迭代。

**理由**：
- 过去四轮（v0.16–v0.19）01 的 MAJOR 全部属于同一类：无辜任务被计数，或毒丸识别不出。没有一条涉及重复发布、伪造远端事实或 manual_only 之后的自动执行。
- 每补一个前提（嫌疑集 → 全局通道 → 排空 → 绑定结束条件），都会暴露下一个未建模的同处工作：本轮是只探测，下一轮可能是心跳或 reconcile 的读操作。原因在于：一个进程里多个任务共享故障域时，仅凭事后快照做精确归因，本来就只能近似。契约层逐轮追加规则收敛很慢，而错误归因的代价只是可用性：
  - 未核销任务被耗尽时，以 release_failed 关闭，没有发布；
  - 已核销任务被耗尽时，进入 manual_only，由人工裁决。

  这两个出口都是安全的。

**契约层至少须保留的规则**：
1. **执行权栅栏**：
   - 单一当前实例与 epoch 栅栏；
   - consume CAS，每个 epoch 至多一次执行许可；
   - 已核销任务的重派须先确认旧实例静默（cgroup `populated=0` 的唯一定义）；
   - indeterminate 锁存；
   - 只探测路径的只读结构约束（FakePublisher 写计数恒为 0）。
2. **manual_only 无自动执行**：C-09、④ 与 execute 派发排除 manual_only；任何延后派发（含暂缓 intent）在发送事务内复核这些守卫。
3. **人工裁决不违背远端事实**：
   - confirm_not_released 须先确认静默且附证据；
   - probe 已证实发生时只允许 confirm_released。
4. **有界性（不规定归因算法，只规定上界）**：
   - 每个 task 的自动重试次数有持久化的上界，计数重启不丢失、按退役事件幂等（同一事件对同一 task 至多计一次）；
   - 耗尽时按授权实际是否已核销分流到上面两个安全出口；
   - 全局另有 fail-stop 上界：launcher 连续失败上界，或跨任务熔断，二选一或都保留，保证没有无限自动循环。
5. **可审计的归因输入**：RetirementEvent（含绑定快照、cause、domain）持久化，使实现期的归因策略可以离线重放和比较；契约只要求"计数对象必须在快照内""计划性回收不计数"。

**可以移到实现期策略的内容**：
- 单绑定才计数的规则；
- 隔离通道及其 open / draining / exclusive 状态；
- 成员排序；
- 熔断阈值；
- 只探测是否参与归因（即本轮的 C19-01）。

契约层改为 conformance 性质：上面 1–5 条，外加"无辜 task 被耗尽的次数"作为**度量项**而非保证项。同时应把 v0.19 中"毒丸至多 1 + max 次被识别""无辜 task 不被他人计数"两句保证语改为目标语，否则契约声明的保证比它能交付的强。

**若采纳**：C19-01 降为实现期待办，第二部分即可 GO。**若不采纳**：C19-01 须按下文修正，修正后仍可能有下一类未建模的同处工作。

### D2. 时间线走查

符号说明：
- P：毒丸。A / B / X：无辜 task。Q：处于 indeterminate、周期发只探测的 task。
- "✓"表示出口唯一且符合声明的性质；C19-xx 表示该格出口不唯一或违反声明，详见对应问题。

| 时间线 | 崩溃点 / 情形 | 出口 | 判定 |
|---|---|---|---|
| 正常 | open，无故障 | 终局 | ✓ |
| 正常 | draining 中新派发 | 暂缓、不计时；回到 open 后先放行 | ✓ |
| 正常 | 暂缓中 task 关闭 / manual_only / indeterminate | 暂缓 execute 作废（superseded） | ✓ |
| 核销前 | P 单绑定，intent 后 ACK 前崩溃 | ② P +1 | ✓ |
| 核销前 | P 与 B 同处 | 都不计，进入通道；P 作为未核销头保持 ready，在 exclusive 下逐次计数 | ✓（CF-AUTH-20m） |
| 核销后发生前 | P 已核销、与 B 同处 | 都不计 → waiting_holder → 静默后 ready → 排空 → exclusive → 计数 | ✓ |
| 核销后发生前 | 成员转 ready 时有普通 execute 在飞 | draining 等其结束；持续新流量不延长 | ✓ |
| 发生后崩溃 | outcome 丢失，单绑定 | +1；恢复臂 → 对账 → released | ✓ |
| 发生后崩溃 | 达到上限 | 未核销 → dispatch_loss_exhausted；已核销 → manual_only | ✓ |
| indeterminate | Q 的周期只探测与单个 execute X 同处，只探测令 broker 崩溃 | 快照 {X} → X +1（误伤）；三次后 X 被耗尽 | **C19-01** |
| indeterminate | Q 的只探测令 broker 崩溃，无 execute 流量 | 快照为空 → start_health；或到 max_start_failures 全局停机，或探测间隔长于稳定期时无限周期崩溃；Q 永不被识别 | **C19-01** |
| indeterminate | 排空时 Q 的只探测在飞 | 无取消命令 → 只能 isolation_drain 换实例 | ✓（C19-03：每次都换实例，正文写法与协议不符） |
| 实例存活、单 task 失联 | A 远端挂起，单绑定 | ① 不适用；② A loss +1 | ✓ |
| 实例存活、单 task 失联 | P 令 broker 半停滞，A 期限先到，快照 {A, P} | 都不计，进入通道（A 排首）；P 在 exclusive 下单独到期时计数 | ✓ |
| 实例存活、单 task 失联 | gerrit 整体变慢，不同 task 依次单绑定到期 | 第二次即触发熔断，launcher 停止拉起，被判为 broker 健康故障 | **C19-02** |
| broker 健康故障 | open，持续流量 | X +1，Y +1 → 熔断停机 | ✓ |
| broker 健康故障 | 间歇型（两次崩溃之间有任务正常完成） | 熔断不触发；每次只计一个单绑定 task，被同一 task 碰上三次的概率低 | ✓（成本可接受，见 C19-02 副作用） |
| 计划性回收 | retire_requested / isolation_drain / 已登记 restart | controlled_reclaim，零计数，唯一事件 | ✓ |
| 任意 | manual_only 之后 | C-09、④、execute 派发、hello 扫描、放行 CAS 均排除；只探测只作证据 | ✓（无自动执行路径） |

**重点问题的结论**：
- **排空能否被无限拖延**：不能。上界是在飞 execute 的剩余阶段期限加一次换实例。awaiting_outcome 的期限可能较长，排空可能持续较久，但有界。
- **毒丸一定在有限次被识别**：execute 毒丸成立；只探测毒丸不成立（C19-01）。
- **无辜不被他人计数**：除只探测同处（C19-01）外成立。
- **熔断误触发 / 被绕过**：单个毒丸不会误触发；远端整体变慢会误触发（C19-02）；间歇型健康故障可绕过，但伤害有界。
- **manual_only 后无自动执行路径**：成立。

### 第二部分问题

#### C19-01 [MAJOR] 只探测流量不在绑定快照内：快照"恰为一个"不能推出"它是肇事者"，只探测毒丸会误伤同处的 execute 或让 launcher 全局停机，且自身永不被识别

- **位置**：01 v0.19 §2.2d L185（总则）、L186（执行绑定）、L188 ②③、L194（排空只处理隔离头时的只探测）、L197（保证语）、L205（周期只探测）。
- **依据**：
  - L185："**计数只在退役时的绑定快照恰为一个 task 时发生**——这是'毒丸有限次被识别'与'无辜 task 不被他人计数'两条保证的共同前提"。
  - L186："执行绑定 = ……阶段 ∈ {awaiting_consume, awaiting_outcome, awaiting_reconcile}……在……转 awaiting_probe（indeterminate）……的事务内结束"。
  - L188 ③："lapsed 时绑定快照为空……→ domain = `start_health`"。
  - L205："**编排周期任务**——对每个 recovery_state = indeterminate 的授权，按 `probe_interval` 向当前 live 实例写 probe 型 DispatchReceipt 并送达"。
  - L197："由此每次计数都发生在绑定快照恰为一个 task 时：毒丸至多 1 + `max_task_interrupts`……次故障后被识别，无辜 task 不被他人计数"。
- **问题**：
  - 快照只含 execute 绑定，但开放状态下实例上还运行着只探测：周期探测、hello 扫描发出的探测、manual_only 裁决前的强制探测，它们与 execute 发往同一个当前实例。只探测路径同样会执行 adapter 代码（只读客户端解析远端状态），对某个特定远端状态崩溃的只探测毒丸与 execute 毒丸同样可能出现。而且 indeterminate 锁存保证它会**每个 probe_interval 重复一次**。
  - 后果：
    - (a) 与单个无辜 execute X 同处：快照 {X} → X +1，三个周期后 X 被耗尽（未核销则关闭，已核销则 manual_only）。这正是 L197 声明不会发生的情形。
    - (b) 没有 execute 流量：快照为空 → start_health → 连续达到 max_start_failures 后 launcher 停止拉起，一个 indeterminate 任务让全部发布停摆。若 probe_interval 长于稳定期，计数每次清零，变成每个探测周期一次的无限崩溃。
    - (c) Q 自身没有任何计数，永不被识别。
  - draining 只在"选中隔离头那一刻"处理在飞只探测，覆盖不了开放状态。v0.17 起"awaiting_probe 不计执行中断"的设计原本是为了不把等待结果的任务算作执行嫌疑，但它同时把只探测的执行风险排除在了归因之外。
- **候选改动**（若负责人不采纳"转实现期"；若采纳，本条降为实现期待办）：

```diff
--- 01 §2.2d 执行绑定（追加只探测绑定）

--- 01 §2.2d 退役事件与归责 ②③
- ② **任务故障**……且绑定快照非空 → domain = `task`：快照恰为一个 task → 该 task 计数……
+ ② **任务故障**……且（执行绑定 ∪ 只探测绑定）快照非空 → domain = `task`：合并快照恰为一个 task → 该 task 计数（执行绑定计 loss / interrupt；只探测绑定计 `probe_fault_count`）；合并快照 ≥ 2 → 都不计数，执行绑定者进入隔离通道，只探测绑定者转 `isolation_state = probe_isolated`——其后续只探测只在通道 exclusive 时作为隔离头发送（只探测很短，独占时间以 probe 超时为上界）；
- ③ **启动 / 健康故障**（cause = `start_failure`，或 lapsed 时绑定快照为空……）

--- 01 §2.5 RetirementEvent / ReleaseTaskState
+     probe_bound_task_ids: tuple[str, ...] = ()        # R19
+     probe_fault_count: int = 0                        # R19
```

  - 被停止自动探测的 indeterminate 任务只能人工裁决。C-11 manual_only 分支"裁决前仍先执行只读强制 probe"须允许"只探测不可用"作为证据，否则裁决无路可走。

#### C19-02 [MINOR] 跨任务熔断把 phase_deadline 计入：远端整体变慢时，被判为 broker 健康故障并停止拉起

- **位置**：01 v0.19 §2.2d L199（跨任务熔断）、L201（launcher）。
- **依据**：L199："任务域内连续 `max_distinct_task_faults`（配置，缺省 2）个**有计数的退役事件**分别落在**不同 task** 上，且其间没有任何 release task 正常完成一个执行可能阶段 → 判定为 broker 健康故障：launcher 停止自动拉起"。
- **问题**：
  - 任务域的有计数事件包括 phase_deadline（loss）。gerrit 或 github 整体变慢、不可达时，不同 task 依次单绑定到期，第二次即触发熔断。launcher 停止拉起、告警为"broker 健康故障"，人工恢复后才清零。
  - 停机本身是安全方向。但诊断错误：broker 是好的，坏的是远端；远端恢复后发布也不会自动恢复，须人工介入。
  - 熔断设计的出发点（上一轮 C18-06）是"进程崩溃与载荷无关"，只应针对 lapsed。
- **候选改动**：

```diff
--- 01 §2.2d 跨任务熔断
- 任务域内连续 `max_distinct_task_faults`（配置，缺省 2）个有计数的退役事件分别落在**不同 task** 上，……→ 判定为 broker 健康故障
+ 任务域内连续 `max_distinct_task_faults`（配置，缺省 2）个有计数的 **lapsed** 退役事件分别落在**不同 task** 上，……→ 判定为 broker 健康故障；phase_deadline 不计入本熔断。连续 `max_distinct_task_deadlines`（配置）个落在不同 task 上的 phase_deadline 事件 → 告警"远端或执行停滞"（计入 R13），不停止拉起
```

- **副作用**：
  - 远端整体故障时，任务按各自 loss 上界关闭或转人工，不触发全局停机。代价是远端长时间不可用时会耗尽较多任务；告警可提示运维暂停发布。
  - 间歇型健康故障（两次崩溃之间有任务正常完成）仍可绕过熔断。被波及的 task 每次只计一次，同一 task 被碰上三次的概率低，伤害有界，不另加规则。
- **配套测试 / 夹具**：CF-AUTH-20i 增加以下用例：
  - FakePublisher 令全部 task 远端超时 → 不触发熔断，产生"远端停滞"告警；
  - FakeBroker 与载荷无关地崩溃 → 仍按 lapsed 熔断。

#### C19-03 [MINOR] 排空所需的"只探测取消确认"在协议中没有载体

- **位置**：01 v0.19 §2.2d L194；§5.1 CommandName（L545–554，21 命令）；L202。
- **依据**：
  - L194："在飞的只探测请求已有界停止（**取消确认**；无法确认时以 `isolation_drain` 计划性回收更换实例）后 → `exclusive`"。
  - L202："probe 超时只重发只探测请求"。
  - CommandName 中只有 `release_probe_dispatch` / `release_probe_report`，没有取消命令。
- **问题**：
  - 没有取消命令，"取消确认"无法实现。实际行为是：排空时只要有在飞只探测，就以 isolation_drain 换实例。
  - "在飞只探测"也没有定义：probe receipt 是 completed 但还没有 release_probe_report 时，算不算在飞？
  - 只要存在 indeterminate 任务（周期探测），几乎每次选隔离头都要换一次实例，这会带来两个后果：
    - 换实例会中断同实例上在飞的 reconcile 读操作；
    - 已核销的 waiting_holder 成员要等新一轮静默。
  - 行为仍然有界、安全，但正文写法与协议不符，实现者会自行发明取消语义。
- **候选改动**：

```diff
--- 01 §2.2d 通道状态

```

- **副作用**：
  - 不新增命令。
  - 多数情况下只探测在超时内返回，不必换实例，换实例的频率下降。
- **配套测试 / 夹具**：CF-AUTH-20k 增加以下用例：
  - draining 时在飞只探测在 probe_drain_timeout 内返回 → 不换实例；
  - 永不返回 → isolation_drain 恰一次，计数零增量。

- **位置**：01 v0.19 L195、L188。
