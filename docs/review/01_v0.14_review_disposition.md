# 01_Contract_Spec v0.14 第十四轮三方复审处置表（→ v0.15）

裁决输入：Kimi **GO**（0 / 0 / 0 / 0）；Codex **NO-GO**（0 BLOCKER / 1 MAJOR / 1 MINOR）；Claude Code **NO-GO**（0 BLOCKER / 1 MAJOR / 1 MINOR / 1 NIT）。合计 6 条意见，归并为 5 个独立问题，**全部采纳**（1 处在两家方案之间取舍，理由写明）。两家的 MAJOR 是两个不同的问题，各自成立。

三家一致确认：周期只探测与持有者回收**不会**形成循环重启（每个持有者至多被回收一次，回收后即静默）；只探测命令**不能**被用来执行发布。

contract_version 由 1.0.0.dev3 升至 **1.0.0.dev4**（新增模型、字段与枚举值属破坏性修改）。

## MAJOR

| # | 问题 | 来源 | 处置与采用方案 | 理由 |
|---|------|------|---------------|------|
| W1 | 静默以"实例 cgroup 的 `cgroup.procs` 为空"判定不成立：实例根 cgroup 的直接进程都退出后，位于子 cgroup 的发布进程仍可存活，根 `cgroup.procs` 照样为空；租约也没有持久化实例 cgroup 绑定 | Codex C14-01 | **采用 Codex**：每个 broker 实例在专属 domain cgroup 中启动，路径与创建代次由 launcher 写入 BrokerInstanceLease；静默按 `cgroup.events` 的 `populated=0`（递归覆盖子树）判定；"已请求 kill"与"子树已空"分开，后者成立才 reclaimed；launcher 崩溃按持久化绑定继续，同名重建不沿用旧证明 | 冻结基线要求"本地不存在在途发布执行"，根目录为空不能证明子树为空 |
| W2 | 阶段期限到期 → 回收 → 恢复 → 再执行没有次数上界：发布本身耗时超过期限时会无限循环，每一轮都杀掉 broker、连带中断同实例上其他 Run | CC C14-01 | **采用 CC，并补未核销分支**：release task 持久化失联次数，达到上限（缺省 2）后不再自动重派——已核销者保持 publishing 只经人工裁决；**未核销者同事务撤销授权、以 release_failed(dispatch_loss_exhausted) 关闭**（授权从未核销，确定没有发布，可以安全关闭；CC 原方案让其停在 release 节点，没有出口）。同实例其他 task 随之重派不计次数。另按 Codex 走查意见写明阶段期限与完成事件以同一事务互斥 | 配置项"期限须足以容纳正常发布"不是协议保证 |

## MINOR / NIT

| # | 问题 | 来源 | 处置 |
|---|------|------|------|
| W3 | "回收完成才拉起新实例"把一个实例的清理变成全局发布停摆，而未核销的 token 由 epoch 隔离即可，不需要等静默 | CC C14-02 | **采用 CC**：launcher 写完 cgroup.kill 即在新的专属 cgroup 中拉起新实例；未核销者立即重派，已核销者与负向映射仍等旧实例 reclaimed。**未采用 Codex 在 W1 方案中"新实例启动须在回收证明成立后"一句**：安全只要求"已核销者恢复执行"与"负向终局"等待静默，epoch 隔离已保证旧实例无法 consume；新旧实例各有专属 cgroup，旧实例的子树判定不受新实例影响 |
| W4 | 新增的只探测出向命令仍沿用执行型的续跑描述与夹具前提（"重放落到 granted/resumed""已核销须先静默"），可能诱导生成非法组合 | Codex C14-02 | 采用。§5.1 按 execute / probe 分述业务续跑；CF-IPC-10 按载荷类型与 recovery_state 分组，probe 只覆盖已核销且 indeterminate，发送不以静默为前提 |
| W5 | phase / phase_deadline / loss_count 没有所属模型，A0 双向检查抽取不到 | CC C14-03 | 采用。新增 ReleaseTaskState 模型并入 A0 |
