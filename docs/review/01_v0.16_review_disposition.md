# 01_Contract_Spec v0.16 第十六轮三方复审处置表（→ v0.17）

裁决输入：Kimi **GO**（0 / 0 / 0 / 0）；Claude Code **NO-GO**（0 BLOCKER / 1 MAJOR / 2 MINOR / 1 NIT）；Codex **NO-GO**（0 BLOCKER / 2 MAJOR / 0 MINOR）。合计 7 条意见，归并为 5 个独立问题，**全部采纳**（2 处合并两家方案）。三个 MAJOR 均不涉及重复发布或伪造远端事实，问题在于计数是否有界、是否误伤无辜任务。

contract_version 由 1.0.0.dev5 升至 **1.0.0.dev6**。

## MAJOR

| # | 问题 | 来源 | 处置与采用方案 | 理由 |
|---|------|------|---------------|------|
| T1 | 崩溃路径上没有"失联触发者"，毒丸任务与同实例的无辜任务每次都各计一次中断；两者回收后又被同时恢复，下一次崩溃仍会一起被波及，最终同时达到上限——一个 Run 的坏计划让另一个已审批 Run 的发布失败 | CC C16-01 | **采用 CC 的嫌疑集隔离**：回收时受影响的 task 若只有一个，直接计数；有两个以上则都不计数，改为按确定序逐个单独重派，单独执行时再崩溃才计数。毒丸至多 1 + 上限次崩溃后被识别，无辜任务不被连带计数 | 只有分开执行才能分清是谁引起的崩溃 |
| T2 | 核销前崩溃的毒丸（broker 在解析计划或核销前就崩溃，阶段为等待核销）落在两个计数之外，可无限重派；已核销任务的恢复派发同样处于这个阶段 | Codex C16-01、CC C16-03 第 1 点 | **合并**：嫌疑集按"该实例已承担未完成的执行派发"识别——以持久化的派发记录与实例绑定为准、不看是否收到 ACK（取 Codex），覆盖等待核销、等待结果、等待对账三个阶段；耗尽后按授权**实际是否已核销**分流，不由阶段名推断（取 Codex） | 不能因为"还没核销"就认为可以无限重试 |
| T3 | launcher 退避以"租约失效"为计数条件，但 broker 在 hello 前就退出时还没有租约，永远不会计数；指数退避拉长间隔后，"时间窗内 N 次"也可能永远不触发；执行期毒丸可能先触发全局停机 | Codex C16-02、CC C16-03 第 2 点 | **合并**：launcher 先持久化每次拉起的记录再启动；启动失败 = exec 失败、hello 前退出、hello 超时、或首个派发送达前失效，按拉起记录恰计一次；连续达到上限即停止自动拉起，退避只决定间隔，稳定运行一段时间才清零（取 Codex）。**派发送达之后的失效归入任务计数、不算启动失败**（取 CC），执行期毒丸先被任务计数识别，不触发全局停机 | 两家分别解决了"计不到"与"计错地方" |

## MINOR / NIT

| # | 问题 | 来源 | 处置 |
|---|------|------|------|
| T4 | 只能人工处理状态下裁决前要求先做只读探测，但只探测命令原来只在"无法确定"状态下合法，其余三种状态发不出去；发不出去时人工仍可选"确认未发布"，正是上一轮要堵的口子 | CC C16-02 | 采用。只能人工处理的已核销任务，在任一恢复状态下都可发只探测命令；结果只作裁决证据、不自动结案 |
| T5 | `waiting_holder` 没有写入和清除点；"只能人工处理"的排除只写在正文、没进状态表的守卫 | CC C16-04 | 采用。写明恢复模式的完整迁移（新增 isolating）；核销、恢复臂、只探测的守卫显式包含 manual_only |
