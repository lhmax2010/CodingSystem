| # | 问题 | 来源 | 处置与采用方案 | 理由 |
|---|------|------|---------------|------|
| R1 | "运行中调用未声明的工具视为部署缺陷"只是责任陈述，没有检测或拦截手段。E0 只做一次子进程观测，覆盖不到罕见分支：某工具的错误处理分支调用了主机预装的 php，观测没走到这个分支，预装包又被当作"无关包"，门禁全绿而 PHP 已被执行 | Codex H211-01、Kimi H211-01 | **合并**：<br>• 取 Codex 的拦截要求：产品宿主侧工具在受控执行视图或覆盖子孙进程的执行准入下运行，视图外或未声明的可执行文件在执行前被拒绝，记 `deployment_dependency_violation`，须补声明、重扫、重验；无法提供这种约束的环境不能以"一次观测无命中"通过验收。<br>• 取 Kimi 的检测要求：launcher 对子孙 exec 记账，deploy 验收时与声明清单比对。<br>• 写明不把构建隔离边界内的业务构建步骤归为产品工具（取 Codex） | 只靠检测时 PHP 已经执行过；只靠拦截则缺少验收证据。两者合起来才闭合 |
| R2 | "命中的字符串是检测签名或期望值"要靠人判断：一个承载完整 PHP 程序的字符串常量也能自称期望值。扫描器安装后生成的 `.pyc` 不在免扫 digest 表里，主机扫描会命中扫描器自己 | CC H211-01 | 采用 CC：<br>• 判据改为 tokenizer 定位在字符串或注释内，且与随策略版本发布的签名表完全相等。<br>• 负向夹具在运行时拼接生成，源码中不得出现以单个字符串常量承载的完整 PHP 程序。<br>• 扫描器以 hash-based pyc（PEP 552）发布，按内嵌源哈希免除，运行时不生成 pyc | 判据可机械执行，免扫范围不扩大 |
| R3 | 例外只比对"批准它的版本"：负责人在后续版本撤销例外后，门禁仍会放行到到期日。被调用工具升级后重新验收时是否重做子进程观测，没有写 | CC H211-02 | 采用 CC：<br>• 例外须同时列在批准版本与现行版本的已批准例外清单中，现行版本删除即撤销。<br>• 清单按固定列序书写，供门禁解析；当前无条目。<br>• 被调用工具的安装件 digest 变化导致重新验收时，重做子进程观测 | 撤销即时生效，观测与工具版本同步 |
