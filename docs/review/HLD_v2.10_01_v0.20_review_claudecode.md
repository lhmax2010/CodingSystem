### 第一部分问题

#### H210-01 [MINOR] 非执行数据分类只对仓库扫描定义，镜像与主机扫描的适用性未写

- **位置**：HLD v2.10 §11.2 L877（"仅命中文本标记时的分类"）、§11.3 L880。
- **依据**：
  - "**仅命中文本标记时的分类（v2.10）**：规范文档、扫描器自身的规则表与单元测试、负向测试的合成清单……**仓内**受审阅、绑定策略版本的固定规则可把它们归为**非执行数据**，只免除'`<?php` 标记'这一文本信号——这些文件不得有可执行位或 php shebang，不得被任何交付物用作入口、模板或解释器输入"。
  - 同段扫描对象："deploy 镜像、构建 VM 镜像与镜像基础层按 digest 展开后的实际安装集与文件……本产品主机上 deploy 清单解析出的安装集与本产品安装前缀"。
- **问题**：
  - 扫描器本身随 deploy 安装：deploy 验收与 E0 要在主机上运行它，它的规则表就在"本产品安装前缀"里。分类若只适用于仓库扫描，主机扫描就会命中扫描器自己的规则表，误伤在主机侧重现。
  - 分类若按路径或文件类别泛化到镜像与主机扫描，任何被打进镜像、类别为"文档"的文件都可以携带 PHP 源码通过。D23 原文"不含 .php 源文件"禁止的是 PHP 源码本身，与是否有解释器无关。
  - "不得被任何交付物用作入口、模板或解释器输入"只能在注册时检查；运行时以数据方式读取（例如 Web 视图提供文件下载）不在检查内。
- **候选改动**：

```diff
--- HLD §11.2 仅命中文本标记时的分类
- 仓内受审阅、绑定策略版本的固定规则可把它们归为**非执行数据**，只免除"`<?php` 标记"这一文本信号——
+ 仓内受审阅、绑定策略版本的固定规则可把它们归为**非执行数据**，只免除"`<?php` 标记"这一文本信号。适用范围：仓库扫描按规则分类；镜像与主机扫描**只**对扫描器自身的规则表按其**文件 digest**（随策略版本发布）免除文本信号，其余文件不作分类——规范文档与合成清单不得进入任何镜像或安装前缀，进入即按文本信号判定。分类文件——
```

- **副作用**：规范文档不能随产品镜像分发。产品不需要在镜像里带规范；若需要，应以不含 PHP 示例的发布版文档另行生成。
- **配套测试 / 夹具**：
  - deploy 镜像中含扫描器规则表（digest 匹配）→ 通过；
  - 规则表被改动（digest 不匹配）→ 失败；
  - 镜像中含 `docs/*.md` 且带 `<?php` → 失败；
  - 主机安装前缀扫描通过（扫描器自身不自触发）。

#### H210-02 [MINOR] "实际调用的工具闭包"与"deploy 安装集 digest"没有机械定义；独立构建主机不在比对内

- **位置**：HLD v2.10 §11.2 L877（主机扫描口径、例外与复核）、B-7 L984、§10 L827。
- **依据**：
  - "本产品主机上 deploy 清单解析出的安装集与本产品安装前缀，以及本产品进程实际调用的工具闭包（含主机预装而被调用者）"。
  - "deploy 安装集的 digest 在验收时记录并写入 execution manifest……Run 创建时与最近一次通过扫描的 digest 比对，不一致即拒绝创建……运维绕过 deploy 直接安装的依赖因此会被发现"。
  - §10："构建隔离边界（同机一次性构建 VM；无 KVM 时为独立构建主机，D22）"。
- **问题**：
  1. **"实际调用"无判定方法**：gbs / mic 是 Python 工具，以子进程调用 rpm、createrepo、qemu 等大量系统工具，这些多半不在其包依赖里。按包依赖算闭包会漏掉被间接调用的预装工具；按运行观测算则不可复现。
  2. **digest 口径未定**：若在验收时对固定包列表算 digest，Run 创建时也按这份列表复算，那么绕过 deploy 升级某工具、引入新的传递依赖（例如 php-cli）不会改变 digest，"因此会被发现"不成立。必须在 Run 创建时从包数据库**重新解析**闭包再计算。
  3. **独立构建主机**：无 KVM 时，构建隔离边界是一台独立主机，其安装集同样会漂移，但 execution manifest 只描述本产品主机。
- **候选改动**：

```diff
--- HLD §11.2 主机扫描口径
- 以及本产品进程实际调用的工具闭包（含主机预装而被调用者）；
+ 以及本产品进程调用的工具闭包——"调用"按**声明**判定：deploy 清单与各 Agent / adapter 注册记录中声明的工具可执行路径，加上这些可执行文件所属包的依赖闭包（按包数据库解析），以及 E0 预检对这些工具执行一次 strace 级子进程观测得到的可执行文件所属包（观测结果写入预检报告并进入声明清单）；未声明而被调用的工具视为部署缺陷；
--- HLD §11.2 例外与复核
- deploy 安装集的 digest 在验收时记录并写入 execution manifest（附录 B 第 7 组同步），Run 创建时与最近一次通过扫描的 digest 比对，
+ deploy 安装集的 digest = 对上述闭包**在计算时从包数据库重新解析**得到的 (包名, 版本, 架构) 排序列表与本产品安装前缀文件树哈希取摘要；验收时记录并写入 execution manifest（附录 B 第 7 组同步），Run 创建时按同一口径重算并与最近一次通过扫描的 digest 比对（构建隔离边界为独立主机时，该主机的 digest 一并比对），
```

- **副作用**：
  - Run 创建时多一次包数据库查询与目录哈希，耗时数秒，可缓存到包数据库 mtime 变化为止。
  - E0 多一次子进程观测，可作为一次性工作。
- **配套测试 / 夹具**：
  - 绕过 deploy 升级 gbs，使其新增 php-cli 依赖 → Run 创建被拒；
  - 独立构建主机安装集变化 → Run 创建被拒；
  - gbs 间接调用、未声明的预装工具 → E0 观测后进入声明清单并参与扫描。

#### H210-03 [NIT] 门禁无法机械区分"负责人修订前提后批准的例外条目"与任何人加入的条目

- **位置**：HLD v2.10 D23 L124、§11.2 L877、B-7 L984。
- **依据**：
  - D23："负责人若修订前提批准某项例外，例外以登记条目（工具名、安装件 digest、所依赖的 PHP 组件、理由、批准人、到期日）进入门禁的例外清单"。
  - B-7："无 PHP 例外清单条目……只在负责人修订 D23 后存在"。
- **问题**：
  - 例外清单是仓内文件，任何有写权限的人都可以加一条带"批准人"字段的条目。"只在负责人修订 D23 后存在"是流程要求，门禁无法校验，与"E0 记录不是许可"的意图不完全一致。
  - 应让条目与 D23 文本互相引用，由门禁比对。
- **候选改动**：


## C. 第二部分：范围调整的独立判断

### C1. K1–K6 是否覆盖本方上一轮要求契约保留的内容

| 上一轮要求 | v0.20 落点 | 判断 |
|---|---|---|
| 执行权栅栏（单一当前实例、consume CAS、每 epoch 一次许可、已核销重派先静默、indeterminate 锁存、只探测只读） | §2.2a、§2.2d 静默 / 执行权持有者 / indeterminate 锁存（未改） | 覆盖 |
| manual_only 后无自动执行；延后派发在发送事务复核守卫 | K3；K5 放行事务按 kind 分型复核 C-09 / ④；hello 扫描与周期探测排除 | 覆盖 |
| 人工裁决不违背远端事实 | §5.1 L644 manual_only 分支 | **本版削弱**（C20-01） |
| 每任务上界 + 全局停止出口 | K2 / K3；K4 ① launcher、② 熔断 | 每任务上界覆盖（计划性回收除外，C20-02）；全局停止出口对"心跳在而执行停住"的 broker 故障缺失（C20-03） |
| 暂缓与独占的活性 | K5 | 覆盖；暂缓项放行失败的去向与 token 占用（C20-04） |
| 可审计、可重放 | K6；RetirementEvent 两份快照 + charged_task_ids + strategy_version | 覆盖 |

### C2. K2 能否在任意归因策略下保证每个任务有界终止

**任务域事件**：成立。
- 每个任务域事件对两份快照中的每个任务各 +1，与是否计数无关。
- 达到 `max_task_affected` 后按 K3 分流到两个安全出口。从不计数的策略同样成立（CF-AUTH-20g (ii) 已覆盖）。
- 只出现在只探测快照里的任务也受约束，不再出现按探测间隔无限崩溃的情形（CF-AUTH-20q）。

**计划性回收域是缺口**：
- `isolation_drain` 是由策略发起的回收，不计任何次数（含 K2）。正文对它的唯一约束来自参考策略的排空条件："执行绑定全部结束后才因只探测换实例"。
- 换一个策略，就可以在仍有执行绑定时反复发起 isolation_drain，被回收的任务没有任何上界。
- 另外两类计划性回收各自有界：retire_requested 对每个 indeterminate 授权在持有者被回收后即可负向映射，至多一次；planned_restart 由人发起。
- 所以"与归因策略无关"在这一点上不成立（C20-02）。

**等待不在 K2 范围内**：
- 已核销任务在"旧 holder 永不静默"时会无限等待。这是 v0.15 起的既有设计：无法证明静默就不能安全重派，只能告警。
- K5 活性条款已要求把它转为可见的暂停状态，不算缺陷。
- 但"每个任务有界终止"在这一处要靠人工清理 cgroup，契约应在 K 总则中如实写明。并入 C20-02 的候选改动。

### C3. 契约条款与参考策略之间有没有矛盾或循环依赖

没有逻辑循环：K 条款不引用 S 条款的结论，S 只在 K 允许的范围内选择计数对象。但有几处契约正文直接依赖参考策略的字段或状态（C20-05）：
- 持有者更替重派扫描写"isolating 者只由参考策略的隔离通道按序派发"；
- recovery_mode 迁移段写"`waiting_holder` 与 `isolating` 下执行类阶段定时器只对 `exclusive` 状态下的隔离头武装"；
- 计划性回收的 cause 枚举含 `isolation_drain`，定义为"参考策略排空时更换实例"；
- K5 的旧通知判定依赖 `selection_seq`，而 S2 说 IsolationChannel 是策略字段、替换策略"可不使用"。

这些不构成矛盾，但替换策略时须同时改契约正文，与"替换后仍须满足 K1–K6、CF-AUTH 不变"的承诺不一致。

### C4. 有没有哪句话仍把策略目标写成契约保证

- L185 总则、S3 已明确为目标与度量，CF-STR-01–04 不计入 conformance。
- K2 的"使归因正确时计数上限先触发"带有条件，不是保证，可以保留。
- 未见残留的保证语。CF-AUTH-20q 期望"loss / interrupt 只可能计给 B（ref-v1 的已知局限，记入度量）"，写法正确。

### 第二部分问题

#### C20-01 [MAJOR] 只探测暂停后的人工裁决可以不经任何远端观测、且不受已记录观测约束，违背"裁决不违背远端事实"

- **位置**：01 v0.20 §5.1 L644（特权运维 manual_only 分支）；§2.2d K3 L194；C-11 L160。
- **依据**：
  - §5.1 L644："**manual_only 分支**：裁决前仍先执行只读强制 probe……probe 明确全部发生 → 只允许 `confirm_released`；明确全部未发生 → 只允许 `confirm_not_released` 且原 holder 已静默；部分出现或 unknown → 沿用既有证据规则；**只探测已因 K3 耗尽而暂停（`auto_probe_suspended = true`，R19）时，强制 probe 按 unknown 处理，evidence_refs 须引用相应 RetirementEvent**，运维可显式发起单次强制只探测（同受 §2.2d K2 结算），负向裁决仍须原 holder 静默"。
  - guard："（verdict∈confirm_* ⇒ evidence_refs 非空）"。
  - K3："只探测通道对其只产出裁决证据、不自动映射终局（C-11a）"。
- **问题**：
  1. 暂停之后，强制 probe 被**直接视为** unknown，而不是先尝试一次、得到 unknown。单次强制只探测是"可以"发起，不是"必须"。于是裁决可以在没有任何新鲜远端观测的情况下进行。
  2. 进入"既有证据规则"后，"evidence_refs 非空"可以只用 RetirementEvent 满足。RetirementEvent 是内部故障记录，不是远端事实。
  3. manual_only 下的只探测结果"只作裁决证据、不自动映射"，所以 Ledger 里可能已有 confirmed_happened 的 ReleaseProbeReport。正文没有规定这类**已记录的确定观测**约束后续裁决。
  - 反例：已核销任务 T 发布实际已发生，broker 在报告 outcome 前崩溃，T 转 indeterminate。
    1. 一次只探测返回 confirmed_happened（T 已是 manual_only，只记录不映射）。
    2. 随后 broker 反复崩溃，T 的 affected 达到上限 → auto_probe_suspended。
    3. 运维裁决：强制 probe 按 unknown；evidence_refs 引用 RetirementEvent；原 holder 已静默 → 允许 confirm_not_released。
    4. Run 以 release_failed 关闭，开发者重新提交，可能再次发布同一变更。
  - v0.19 之前，manual_only 分支每次裁决都先做新鲜的强制 probe，远端事实是持久的（已合入的变更一直在），所以"已发生"几乎总能被重新观测到。v0.20 为了让暂停后有出口，绕过了这道约束。
- **候选改动**：

```diff
--- 01 §5.1 特权运维 manual_only 分支
- **只探测已因 K3 耗尽而暂停（`auto_probe_suspended = true`，R19）时**，强制 probe 按 unknown 处理，evidence_refs 须引用相应 RetirementEvent，运维可显式发起单次强制只探测（同受 §2.2d K2 结算），负向裁决仍须原 holder 静默；
+ **已记录观测的约束（R20）**：该授权任一已落账的 ReleaseProbeReport 为 confirmed_happened（全部目标）→ 只允许 `confirm_released`；部分目标已证实发生 → 不允许 `confirm_not_released`。**只探测已因 K3 耗尽而暂停（`auto_probe_suspended = true`，R19）时**，裁决前须由运维显式发起一次单次强制只探测（同受 §2.2d K2 结算）：有确定结果按上句与本分支前述规则约束；该次只探测失败（实例退役或超时）才按 unknown 处理。unknown 下 `confirm_not_released` 的 evidence_refs 须含至少一条**远端证据**（只探测报告或外部系统记录引用），RetirementEvent 只作附加引用、不计入"证据非空"；负向裁决仍须原 holder 静默；
```

- **副作用**：
  - 暂停后的裁决多一次只探测，若再次导致崩溃，仍只增加 K2 次数，不形成循环（任务已耗尽，K3 不再动作）。
  - "远端证据"需要在 AdjudicateRequest 的 evidence_refs 上区分类型（内部事件 / 只探测报告 / 外部记录），模型增加一个判别字段。
- **配套测试 / 夹具**：CF-AUTH-20j / 20q 增加以下用例：
  - 已有 confirmed_happened 报告的 manual_only 任务，暂停后裁决 confirm_not_released → 拒绝；
  - 暂停后未发起单次强制只探测即裁决 → 拒绝；
  - 单次强制只探测导致实例崩溃 → 按 unknown，evidence_refs 只有 RetirementEvent → confirm_not_released 被拒，附外部记录 → 允许（仍须静默）；
  - 部分目标已证实发生 → 不允许 confirm_not_released。

#### C20-02 [MINOR] 计划性回收不计任何次数，而 isolation_drain 由策略发起：K2 的上界在替换策略下不再与归因无关

- **位置**：01 v0.20 §2.2d L189 ①、L193 K2、L185 总则。
- **依据**：
  - ①："计划性回收（cause ∈ {`retire_requested`……；`isolation_drain`——参考策略排空时更换实例；`planned_restart`……}）→ domain = `controlled_reclaim`：不增加任何计数（含 K2）"。

  - L185："契约保证的是：每个 task 的自动恢复次数有界"。
- **问题**：
  - isolation_drain 由策略在排空时发起，契约对它没有任何限制。参考策略只在执行绑定全部结束后、因只探测换实例才发起它，所以被回收的实例上没有执行任务。

  - 另外两类计划性回收各自有界，不受影响：retire_requested 对每个授权至多一次（持有者被回收后即可负向映射）；planned_restart 由人发起。
  - 附带：L185 的保证应如实写明，旧 holder 永不静默时的等待不在"有界终止"之内，只保证可见与告警（K5 活性）。
- **候选改动**：

```diff
--- 01 §2.2d 退役事件与归责 ①
- `isolation_drain`——参考策略排空时更换实例；
+ `isolation_drain`——策略在独占排空时更换实例，**只允许在该实例 `bound_task_ids` 为空时发起**（判定事务内校验，不满足即拒绝提交并告警）；
--- 01 §2.2d K2
- 任务域事件同事务对两份快照中的每个 task 的 `affected_count` +1
+ 任务域事件、以及 cause = `isolation_drain` 的计划性回收事件，同事务对两份快照中的每个 task 的 `affected_count` +1
--- 01 §2.2d L185 总则
- 契约保证的是：**每个 task 的自动恢复次数有界、耗尽时落在安全出口；
+ 契约保证的是：**每个 task 的自动恢复次数有界、耗尽时落在安全出口（等待旧 holder 静默不是自动恢复：无法证明静默时只保证可见的暂停与告警，见 K5 活性）；
```

- **副作用**：
  - 参考策略不受影响：它的 isolation_drain 本来就只在执行绑定为空时发生，只探测快照中的任务多计一次 K2，量级可忽略。
  - 替换策略失去"用计划性回收规避上界"的可能，这正是本条的目的。
- **配套测试 / 夹具**：CF-AUTH-20n 增加以下用例：
  - 执行绑定非空时发起 isolation_drain → 拒绝提交并告警；
  - NullAttribution 策略 + 反复 isolation_drain（仅有只探测在飞）→ U 在 max_task_affected 次后进入 K3 出口。

#### C20-03 [MINOR] 期限型 broker 故障没有全局停止出口

- **位置**：01 v0.20 §2.2d L195 K4、L185 总则。
- **依据**：
  - K4："phase_deadline 事件不进入该窗口（远端整体变慢不应被判为 broker 故障而停止拉起）：同一窗口内不同 task 上的 phase_deadline 事件达到 `max_distinct_task_deadlines`（配置）→ 告警'远端或执行停滞'并计入 R13，**不停止拉起**，各 task 仍受 K2 / K3 约束"。
  - 总则："全局有停止出口"。
- **问题**：
  - 这一条源自本方上一轮 C19-02（期限到期不应让 launcher 停机）。但"心跳正常而执行线程卡死"的 broker 故障只表现为期限到期，与远端整体变慢无法单凭期限区分。
  - 现文下，这类故障中每个任务各自有界，但系统层面没有停止：实例被不断以期限退役、替换，新任务持续进入、持续被耗尽（未核销者关闭、已核销者转人工），只有告警。
  - "全局有停止出口"对这一类故障不成立。
  - 停止拉起 broker 不是合适的出口（远端变慢时无益）；合适的是**暂停新发布派发**。两种根因下继续派发都只会制造更多耗尽任务，而暂停派发不影响已在途任务的恢复与对账。
- **候选改动**：

```diff
--- 01 §2.2d K4
```

#### C20-04 [MINOR] 暂缓项放行复核不通过时的去向未写；只探测暂停不作废已暂缓的自动 probe，token 被占住

- **位置**：01 v0.20 §2.2d K5 L198（放行事务）、L199（作废）、K3 L194；§2.5 L354（同 token 至多一个 intent）。
- **依据**：
  - K5 probe 放行："复核 Run = publishing、授权已核销且（recovery_state = indeterminate ∨ recovery_mode = manual_only）、`auto_probe_suspended = false`（或为运维显式发起）"。
  - 作废："task 终结时，暂缓的 execute 与 probe 同事务作废；转 indeterminate 或置 manual_only 时只作废暂缓的 execute，仍合法的暂缓 probe 保留"。
  - §2.5："同一 token 任一时刻至多一个 state=intent 的 receipt……第二个 intent 拒绝"。
- **问题**：
  - K3 的只探测耗尽事务同时置 manual_only 与 `auto_probe_suspended = true`。按作废规则，置 manual_only 时暂缓的 probe"仍合法"而保留。但它是自动探测，放行复核要求 `auto_probe_suspended = false`，于是每次唤醒都放不出去。
  - 正文没有写放行复核不通过时暂缓项怎么办：作废，还是继续暂缓。
  - 若继续暂缓，这条 intent 一直占住"同 token 至多一个 intent"，运维的"单次强制只探测"写不进来，C-11 manual 分支的强制 probe 也无法执行。结合 C20-01 的修正（暂停后裁决须先做一次强制只探测），这条路径会把人工裁决卡死。
  - CF-AUTH-20o 的期望"不留阻塞 token 的废弃 intent"表达了正确意图，但正文规则没有覆盖这种情形。
- **候选改动**：

```diff
--- 01 §2.2d K5 作废
- **作废**：task 终结时，暂缓的 execute 与 probe 同事务作废（state := superseded，superseded_by 指向关闭事件）；转 indeterminate 或置 manual_only 时只作废暂缓的 execute，仍合法的暂缓 probe 保留。
+ **作废**：task 终结时，暂缓的 execute 与 probe 同事务作废（state := superseded，superseded_by 指向关闭事件）；转 indeterminate 或置 manual_only 时只作废暂缓的 execute，仍合法的暂缓 probe 保留；置 `auto_probe_suspended = true` 的事务同时作废暂缓的自动 probe。**放行复核不通过**（守卫、模式或暂停条件不满足）时，该暂缓项在放行事务内作废（superseded_by 指向本次复核），不得以暂缓状态继续占用"同 token 至多一个 intent"；条件恢复后由相应发送点重新生成。
```

- **副作用**：无。暂缓项是可重建的派发意图，作废后由发送点按当前模式重建，不丢失语义。
- **配套测试 / 夹具**：CF-AUTH-20o 增加以下用例：
  - 暂缓自动 probe → K3 置 suspended → 该项同事务作废，运维单次强制只探测可写入；
  - 放行复核不通过（模式已变）→ 作废，不阻塞 token；
  - 条件恢复后发送点重建新 intent。
