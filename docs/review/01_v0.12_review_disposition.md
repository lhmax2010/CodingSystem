## MAJOR

| # | 问题 | 来源 | 处置与采用方案 | 理由 |

| Y1 | DispatchReceipt 的 intent 跨 broker 实例更替时卡死：§2.5 要求"intent 无 completed → 同 request_id 重派"，§2.2d 要求"换 epoch → 写新 intent（新 request_id）"，又约束"同 token 至多一个 intent"。旧实例受理后 ACK 前崩溃，新实例上线后两条规则都走不通 | Codex C-01、CC C12-01 | **两家方案一致，采用**：receipt 状态增 `superseded`，带 `superseded_by` / `superseded_at`。恢复规则按 target_epoch 互斥：(a) target_epoch == 当前 epoch → 同 request_id 重送；(b) 不等 → 替代协议，一个 Ledger 事务内把旧 intent CAS 为 superseded 并写新 intent；已核销的 token 须先满足静默。superseded receipt 的迟到 ACK 只写审计，不完成新 receipt、不恢复旧执行权。CF-IPC-10 扩充实例更替三个崩溃点 × 核销前后两种前提，以及迟到 ACK、"尚未发送又换实例" | — |
| Y2 | "静默"谓词的两个分量在 01 中没有来源：broker task lease 没有机制；pgid 由 broker 自报、编排未复核；编排不是 broker 父进程，"reap"无从谈起。另：broker 实例存活但某个 release task 失联（lease 丢失）时，target_epoch 不变，重派扫描永远选不中 | CC C12-02、Codex C-03 | **合并**：取 CC——实例身份由编排经 SO_PEERCRED + /proc（pid、pgid、starttime）核实，hello 载荷只作回显、不符即 FORBIDDEN；新增 `BrokerInstanceLease`（live / retiring / lapsed / reclaimed）与 broker socket 心跳，断连超过租约时长 → lapsed 并触发静默判定；静默判据写明"pgid 下无存活进程（含 fork 出的子进程）"与"pid 被复用但 starttime 不同即判静默"。取 Codex——task 级失联令实例进入 retiring：拒绝其执行类命令，由 supervisor 清理并起新实例，新 epoch 下按 Y1 恰一次恢复；无法清理则不重派并告警 | CC 解决了"静默从哪来"，Codex 解决了"实例活着但 task 丢了"这条 CC 未覆盖的时间线；把 task 级失联升级为实例更替，复用已验证的 epoch 恢复路径，不必另造 task 级 epoch |
