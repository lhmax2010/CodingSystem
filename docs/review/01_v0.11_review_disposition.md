## BLOCKER

| # | 问题 | 来源 | 处置与采用方案 | 理由 |
|---|------|------|---------------|------|
| X1 | gate 的 waiting→resolved CAS 在 decision_submit 与 outbox 消费（C-08a/b）各做一次——决定提交后 gate 已 resolved，消费必失败，paused Run 无法 resume、running 中 gate 无法 dispatch 下游 | Codex C-01 | **采用 Codex**：gate CAS 只在决定事务（或 C-08c TTL）中发生一次；C-08a/b 的 guard 改为"outbox_id 未消费（inbox CAS）∧ gate 已 resolved 且与 outbox 一致"；C-08c 改为写同形 outbox、决定与 TTL 仅一方胜出；CF-SM-02/10、CF-IPC-04 改为真实串联 | 冻结 HLD §4.4 明确 gate CAS 属于决定事务；判决状态与送达状态应分开 |
| X2 | 恢复许可的 receipt 未按 epoch 隔离：E1 获 Proceed 后崩溃，E2 以同一逻辑 request_id 上报会复用旧许可、跳过本轮复核；旧实例晚到的 release_failed 可关闭新实例的当前执行。另：现实中的 ACK 丢失（断连重连）在 v0.11 下三种重投方式都拿不到 granted；epoch 计数器未持久化；hello 自身幂等未定义 | Codex C-02（BLOCKER）、CC C11-02（MAJOR） | **合并采用**：epoch 按 **broker 进程实例**分配（实例身份含 start_time），计数器持久化于 Ledger，同一当前实例重连返回同一 epoch，低于当前 epoch 的实例 hello 被拒——任一时刻只有一个当前实例（取 CC）；broker 入向幂等域改为 **(broker_epoch, command)**，新实例复用 request_id 落入新域（CC 的实例域 + Codex 的 epoch 隔离，二者在"一实例一 epoch"下等价）；`recovery_state` 与"每 epoch 至多一次许可"（取 Codex 的 execution_permitted 思路 + CC C11-06 的状态枚举）；C-10/C-10a 校验连接 epoch == granted_epoch（两家共同）。**不采用** Codex 的"按连接分配 epoch + 载荷携带 epoch"，**也不采用** CC 的"consume 投影剔除 broker_epoch" | 按连接分配 epoch 正是 CC 指出的断连即换 epoch、ACK 丢失后取不回 granted 的根源；按实例分配后同实例同 epoch，载荷 epoch 不变，投影无需特殊处理 |
