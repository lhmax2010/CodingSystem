## 3. 任务 B 结果

1. **YAML loader / CF-DSL-FLAG：反对。**

   逐 token 复演结果：

   - `on:`：移除 bool resolver 后得到字符串键，已修复。
   - `join:pre_final_review`：冒号后无空白，保持普通字符串，正确。
   - `value: 5.0`：在步骤①已被 SafeLoader 构造成 float，步骤②无法再取得“原文词素”，因而无法区分 `5.0`、`5.00`、超 scale 写法等。

   此外，本机 PyYAML 6.0.1 按文档所述仅移除 bool/timestamp resolver 后，实测 `true` 变成字符串、`010` 仍按 YAML 1.1 解析为整数 8，证明它不是所声明的 YAML 1.2 core schema。应使用 token/node 层预处理或完整固定 resolver/constructor，并在对象构造前处理 value 词素。

2. **自足性：反对。**

   仍存在三类违例：

   - 规范性外引：§3.1、§3.4、§4.2、§5.3。
   - 无完整定义的具名类型：CreateRunRequest/Response、SubmitPatchRequest/Response、RunStatusResponse、PendingEvent、EffectError、TraceEvent 等。
   - 匿名载荷：Skill 表、控制面命令表、RunStatusResponse.snapshot、Report 类型体。

   尤其 §4.2 没有真正给出 HLD 附录 B-4 要求的六态迁移/查找矩阵。

3. **reconciliation worker：反对。**

   进程隔离方向正确，且原 R3-08 可以关闭；但恢复协议尚未成为可实现契约。当前没有定义 probe dispatch/result 的具名消息、记录版本绑定、执行租约、超时、崩溃后 `probe_attempts` 在哪个提交点递增，以及陈旧 worker 结果如何 CAS 拒绝。CF-EF-02 只覆盖逻辑结果矩阵，没有覆盖 reconciliation worker 在派发前、执行后、回写前崩溃。

4. **审批—核销—执行链：反对。**

   token_id 的生成方、ReleasePlan 头、ci_plan_task_id 来源和 broker digest 重建均已改善，但 reviewer 在 IPC 两跳间丢失：

   `Review CLI(peer UID) → Approval 服务(得到 reviewer) → decision_submit{ApprovalDecisionRequest}(无 reviewer) → 编排 Ledger`

   编排进程不能从 Approval socket 的 peer credential 反推出真实 CLI 用户。与此同时，§0.2 称 decision_id 由 Approval 服务生成，内部 Request 又不携带 decision_id；token_id 返回也没有响应 schema。建议区分外部 CLI 请求与内部可信 `DecisionSubmitCommand`，后者携带服务端认证得到的 reviewer，并明确 decision_id/token_id 的唯一生成方及响应联合。

5. **§6 conformance 权威：反对。**

   - 多个 case 仍聚合在一行，缺具体输入 fixture。
   - compiler_bench_only“原文”未在本文或指定稳定资源中提供。
   - CF-EF-02 未覆盖 `supports_probe=true ∧ replay_safe=true`，但 §4.3 的 `not_supported + replay_safe` 分支依赖该组合。
   - CF-EF-05 的异参/旧同键期望与 idem_key 定义矛盾。
   - HLD §11.3 要求的静态 effect_call_id 唯一性拒绝、已存在 blob 内容被篡改后的 digest 检测等没有独立 case。
   - CF-DSL-PROP 只明确断言 V-09/V-11，没有覆盖 HLD 要求的可达环 budget、release 必经 hitl 等随机图性质。

   因此 07 harness 仍需自行补充规范，而非仅执行本文期望。

## 3. 任务 B：仲裁关注点

**B-1（loader 定案的原文字节可实证性）：接受，附一条粒度勘误（M-02，MINOR）。** 逐 token 复演 HLD §4.2.1 原文：`on:` 键——bool resolver 移除后保持字符串键（PyYAML 1.1 的 `on`→True 坑被根除，这正是 v.3 修复漏掉 loader 本身的实证点）；`join:pre_final_review` 冒号词素——flow mapping 内 `to: join:pre_final_review`，`:` 后随非空格字符，YAML 1.2 plain scalar 规则下解析为完整 ✓；`5.0` 词素路径——预处理四步序中②在 compose 节点层取原始词素（SafeLoader compose 保留 scalar 原文），按十进制词素校验、scale 补零转 "5.00"，非十进制词素（如 `1e3`）在词素正则处拒绝 ✓；四步序（loader 读字节→词素化→标量 to 列表化→pydantic 校验顺序无环可执行。CF-DSL-FLAG 以原文字节加载为断言，可实证。布尔 resolver 移除粒度问题见 M-02。

**B-2（自足性）：接受，附一处违反（M-01，MINOR）。** 全文通读 + 外引扫描：§1.2/§3.2/§3.6/§4.1 均已内联（JsonValue、SysOutcome、ReportEntry、Producer 联合等全部就地定义）；全端点具名模型（CreateRunRequest·Response 等并入 A0）；§6 聚合行已展开为逐 case；未发现匿名载荷与未定义类型名。**例外一处**：§4.2"迁移表（v0.1 基础上两处）"仍以外引承载规范内容——迁移表全边集需回查 v0.1 才能完整重建，与文档头部"不再以外引承载任何规范性内容"的声明直接矛盾，且 CF-EF-01"迁移表全边尝试"需要权威边集在本文档。

**B-3（reconciliation worker 接合）：接受。** 分工闭合：probe 在无 Ledger 写权限的专用 worker 内执行（业务代码不入单写者进程）、编排进程仅据返回提交状态迁移（与 Ledger 单写者一致）；probe_attempts/next_probe_at 持久化重试进度，与 §4.3 indeterminate 有限重试映射及 CF-EF-02 单元格规则逐项对应；只读无副作用断言入 conformance；心跳/进程组语义复用 §5.1.2 既有机制（编排失联→killpg 自杀对 reconciliation worker 同样成立）。命令面细节见 CLARIFY-1。

**B-4（审批核销-执行链载荷闭环终核）：接受。** 以写代码标准逐步走通：Approval 服务收 CLI 决定 → decision_submit{ApprovalDecisionRequest}（无 id、无 reviewer——reviewer 由 peer credential 映射生成，不符拒绝并审计）→ 编排事务内新鲜度 CAS + 生成授权记录（token_id/decision_id 服务端签发，与 §0.2 一致，Approval 不产 ID 消解了上轮生成方矛盾）+ gate CAS + outbox（含 token_id）→ release_dispatch{…, release_plan_ref, token_id} → broker  token_id 读授权取 manifest digest、依 release_plan_ref 重建 canonical Manifest 比对 → authorization_consume 三支 → 执行。每一跳的发起者、载荷、事务边界、失败归类均有定义，无缺口。

**B-5§6 终核）：接受。** 逐 case 行已全部展开（CF-DSL-01a/b、10a/b、13c 补齐了 v0.3 的聚合盲区；CF-AUTH-03..06、CF-IPC-01..05、CF-BLOB-01..04、CF-SKILL-01..06、CF-DC-01..05 逐行化）；CF-ACT-08 stale 到达 case 补上 HLD"陈旧 series 进 join 拒绝"最后一个映射点；矩阵单元格规则（CF-SM-01、CF-EF-02/05）可机械枚举，CF-EF-05 的 failed 单元格按 disposition 展开后语义与 HLD"依类别策略"一致。HLD §11.3 类别逐类对账：零残漏。
